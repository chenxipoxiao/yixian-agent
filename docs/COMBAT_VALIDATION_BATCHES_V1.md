# 战斗规则按批修复与验证

2026-11-13 用户要求：先批量修复，再统一测试；不再每修一张牌就重跑所有回放。

此约定更新后续 S2 的验证频率。已冻结的战斗版本、历史测试结果及阶段验收条件保持原样。配置见 `configs/combat_validation_batches_v1.json`。

## 工作顺序

1. 从最新缺口队列选一批相关效果，通常 3–8 项，按依赖关系调整数量。把同场缺少的卡牌、仙命、状态和复制/升级联动尽量放在同一批，避免每补一个前置就做一遍全量测试。
2. 逐项核对来源并完成整批实现，保留旧版本。一起补对应边界检查；单纯编辑过程中不逐项跑全量回放，也不逐项上传到服务器做全量复测。
3. 冻结这批改动、来源、依赖和待测回放。一次运行相关边界检查和受影响的完整战斗：取双方开战卡牌、仙命、百家、永久状态及明确依赖的并集，补 4 条固定对照。手牌复制来源也需纳入；所有改变的等级/变体 ID 均要登记。
4. 局部失败先修这一批，重跑相关检查。确认整批可用后，对最终候选做一次全量开发回放回归，再统一在服务器验证该批。不要在本机每完成一项就两端全量跑。
5. 按整批结果发布覆盖率及剩余差异，推进下一批。改动影响伤害、先后手/初始化、行动调度、死亡/复活或命元结算等公共逻辑，或者依赖范围不明时，整批直接全量检查。

## 新入口

`tools/validate_combat_batch.py plan --spec <批次说明.json> --out <冻结计划.json>` 固定来源与候选源码哈希，并保存筛选结果及每条入选原因。

说明文件包含 `batch_id`、`pilot`、`context`、`baseline`、`engine_module`、`settlement_module`、`source_sha256`（候选文件相对路径到哈希的映射）、`changes` 和可选 `control_count`。路径指向项目内现有开发来源，不能替换为保留测试局。版本化引擎和结算模块、批次工具必须包含在源码清单中。

每项改动登记 `name`、`scope`、`dependency_review`、`dependency_complete`，以及相应 `card_ids`、`fate_ids`、`season_ids`、`permanent_ids`、`character_ids`。依赖不完整或公共逻辑范围自动选全部记录。相关复制/升降级消费者的 ID 与全部受影响牌级也放入同一清单。

`tools/validate_combat_batch.py run --plan <冻结计划.json> --out <局部结果.json>` 只跑计划并集，使用原来相同的开战初始化、诊断种子、同速条件和四项终局核对流程。

整批完成后使用同一入口加 `--full`。候选源码或上下文改变后必须登记新候选计划，不能沿用已通过的全量结果。旧入口仍可复现历史实验。

## 结果口径

- 局部报告只统计实际新执行的回放；其余标为“本次未测”，不会把旧缓存当作刚刚测试通过。
- 筛选只使用开战资料，不以终局胜者、生命差或旧匹配情况挑样本。固定对照按记录 ID 的哈希选择。
- 筛选是提高开发效率的保守线索，不是证明其他回放绝对不受影响。未登记的动态生成/跨卡依赖可能遗漏，所以整批发布仍需一次全量回归。
- 若改变开战上下文，必须声明全量范围；阻断记录保留原因，不能从统计中消失。确定性与随机、记录条件样本继续区分。
- 工具不会自动晋级 S2、生成训练标签或认定实战强度；全量通过仍需原有规则证据和人工研究审查。

本次仅更新验证流程，不改变 v49 战斗与 v47 结算规则。用既有玄灵附身记录及固定对照验证新入口时，应与已冻结 v49 报告逐项一致；不因此重跑 525 条作为额外的规则改版。
