# 龙瑶分阶段训练与持续迭代

目标是当前赛季的龙瑶完整对局离线策略。每阶段都先验证数据、规则和动作，再训练，
用独立评测决定是否进入下一阶段。机器可读计划在 `configs/training_stages.json`。
其中样本量、决策量与验收阈值是本项目的初始研究安排，不是已证明的强度保证。

| 阶段 | 训练内容 | 通过条件与当前状态 |
| --- | --- | --- |
| S1 回放预训练 | 从已有牌组学习真人牌序；自己生成前缀的整组排牌评测 | 已验收：1226/150/123局、3预登记种子完成；一次固定测试，均无非法或改变牌数输出。主模型完整牌序复现21.14%，位置频率基线5.76% |
| S2 对战摆牌 | 在固定且已验证的龙瑶、云剑、副职和仙命范围内，按真实战斗奖励优化摆牌 | 先解决清单内的规则和触发交互，确定性校准没有未解释差异；再比较预训练与同预算从零训练。当前战斗校准尚未通过 |
| S3 单轮经营 | 选牌上阵、合成、炼化、换牌、升本、普通/百家仙命，最后放开副职选择 | 合法动作和资源账本齐全，1000次随机流程核验零账本错误；从10万、100万决策逐级训练 |
| S4 八人整局 | 一个龙瑶学习席位对七条连贯回放对手轨迹，执行配对、命元扣除、淘汰和名次奖励 | 先通过100局完整流程核验，零测试战果训练标签、零不明结算、零资源重置；再逐级扩大PPO训练 |
| S5 独立评测 | 比较脚本、受限搜索、上一版模型，检查新时间段及困难对手 | 3个训练种子，初始每模型1000局评测，按独立对手来源计算置信区间；保存稳定版本及实战观察接口计划 |

S2、S3的规则实现可以在S1数据准备期间推进，但训练升级必须有对应阶段的通过证据。
回放没有换牌、炼化、升本等完整操作轨迹，不把推测动作当作真人标签。
现有 `flow` 默认测试战果不能进入强化学习。牌序复现率、离线战斗胜率和真实段位分别记录。

## 版本迁移讨论与现有接口核对（2026-11-12）

用户提出开局百家、副职会强烈约束构筑路线，以及版本变化不应默认从零训练。
这两点仍为待检验的设计判断，当前阶段、已冻结模型与训练配置不变。
原始回放确有普通仙命、道韵和百家的累计候选与选择；信息提取范围和选择前状态应分别核对，
不能把缺少逐次换牌过程误写成所有经营决策都没有记录。

本轮只读核对显示现有S1模型输入为卡牌ID、已构造前缀和可选掩码，没有当前卡牌数值/效果特征；
词表及源码与推理权重契约一致，导出不含优化器，训练器没有精确恢复入口。
拟讨论的迁移方式为：固定旧环境与权重、列出规则/牌池/动作差异、在新规则下复测，
显式迁移兼容参数并对受影响局面训练，再检查整体表现和对手分布变化。
数值改动不必重置所有参数，但少量改牌也可能影响整个构筑体系，不能按改牌比例承诺算力节省。
旧回放可作有版本标记的行为证据；改变规则后的战果、回报和PPO优势值不能直接沿用。
保留旧策略的约束也只能作用于仍然适用的行为，不能阻止学习新版本更好的选择。

审计证据见`runs/stages/20261112T015000Z-version-transfer-audit/version-compatibility-audit.json`。
本轮没有跨版本性能实验、GPU训练、回放/保留集读取或模型接口修改。

## 每轮工作

每30分钟在本对话继续一次巡检与迭代。先读 `AGENTS.md`、阶段计划、最新阶段记录、
训练报告和研究账本，再运行服务器检查。

```powershell
.\.venv\Scripts\python.exe -X utf8 tools/monitor_training.py --ssh
```

检查GPU占用与温度、磁盘、训练进程、损失/评测记录更新时间、模型文件和退出状态。
报告保存在 `runs/monitoring/`；完成的任务不误报为停滞，也不因GPU空闲就重复训练。
若SSH不可达则留下失败记录，继续可以离线完成的数据或代码工作。

有训练在运行时，先确认是否正常，不重复启动。服务器空闲时，从当前阶段选择一项
有明确结果的工作：补规则、修已定位问题、扩充数据、补评测，或启动已登记的新实验。
相同配置和数据无新假设时不重跑；同一原因连续失败两次先修原因。
每轮完成后写新的阶段快照和研究事件，保存验证证据、未完成项与下一步。

初始使用现有单卡T4，最多一个训练任务。新任务设置不超过2小时的运行上限，
2026-11-12用户确认单T4已包月：取消每日6小时上限，允许全天持续使用。仍只运行一个GPU任务，单任务按不超过2小时分段，便于检查点保存和失败恢复；有合格新实验可连续安排。保留实际耗时与历史预留账本，账本不再因累计超过6小时阻止启动。单批回放下载不超过192MiB，每日不超过1GiB。
这些限制由每轮启动前核对与训练配置落实，监控脚本本身只读，不会杀进程或购买资源。
监控的“可启动”仅表示服务器空闲且健康，还需要通过阶段、预算及数据验证。

## 数据与模型记录

- 按整局隔离所有回放视角，重复状态不算新对局。数据和源码都记录哈希。
- 验证集选择模型；测试集仅在方案冻结后检查。已用于诊断或调参的测试集降为开发证据，另留新测试局。
- 不覆盖历史实验或失败结果。部署修改前保存相应源码，模型只按兼容契约加载。
- 新训练任务保存配置、优化器与随机状态；未实现恢复入口时不能宣称精确续训。
- 保留服务器所有研究检查点；本机取回报告和选定权重，校验后再标记备份完成。

首次迭代据此优先扩充独立数据并冻结新评测集合。

原来45个测试局保留为历史证据，不纳入新的独立最终测试。
当时可组合893个训练局、110个验证局和67个新测试局，尚未达到S1的数据门槛。
第二次迭代又采集8个档案、新增429局，并冻结 `runs/pretraining-data/longyao-s1-frozen-v2`：
训练1226局/18580牌阵，验证150局/2229牌阵，未评测测试123局/1807牌阵。
旧45测试局从新语料所有划分排除，各来源原整局划分保持不变；本机和服务器已核对文件哈希。
语料使用登记见 `configs/longyao_corpora.json`。数据数量门槛通过，暂不需要追加采集；
后续三种子训练和一次固定保留测试已完成，S1已验收。当前进入S2规则校准；这些成绩不代表完整对局能力。

## 训练与测试隔离

`tools/train_longyao_development.py` 是新的训练/验证入口。它要求固定语料清单哈希、
相互独立的训练与验证随机流，拒绝test角色和test随机种子，也不会为检查哈希而打开test文件。
合成测试在完全没有test文件的情况下完成两次CPU更新、保存和重新加载所选检查点；
实际新语料的加载检查只打开manifest、train和validation。
上一轮实现阶段的15项相关测试在服务器全部通过；本机14项通过，PyTorch集成测试因依赖缺少跳过。
这些是软件验证；后续真人语料训练与验收结果见下文。

`yixian/order_evaluation.py` 分开统计：给定真人前缀时的下一张复现率/NLL，
以及全程使用自身预测前缀的完整牌序一致率/位置复现率。解码逐次消耗可用卡牌实例，
拒绝非法输出并检查多重集不变；随机完整牌序基线按重复牌的排列数精确计算期望。
除汇总指标外，配对区间按整局重采样，针对每局指标等权平均，不能解释成战斗胜率区间。

独立最终测试入口及一次性使用登记已完成，并已用于本轮冻结的3模型评测。
当前123个保留测试局已用，后续不得再称为未使用测试集。不能调用原v1训练器批量训练，因为它每次都会评估test。
新入口保存v2训练契约和全部相关源码；原模型/输入代码、v1训练器和v1推理入口未改写。
v2检查点已支持契约检查与推理加载接口；保存了优化器/随机状态不等于已支持精确续训。

## S1本轮验收结果

冻结计划为 `runs/campaigns/20261111T153452Z-longyao-s1-v2/plan.json`。

验证集在测试前选定种子20261122为主模型，并固定全部3个模型一起评测，不按测试结果重新选择。

| 种子 | 自身前缀完整牌序复现率 | 真人前缀下一张复现率 |
| --- | ---: | ---: |
| 20261121 | 20.70% | 69.18% |
| 20261122（验证选择的主模型） | 21.14% | 69.24% |
| 20261123 | 22.03% | 70.18% |
| 位置频率基线 | 5.76% | 41.92% |
| 随机期望 | 1.67% | 26.81% |

这些是123个完整来源对局、1807个牌阵上的汇总复现指标；3模型均无非法或改变多重集输出。
按每个来源对局等权统计，主模型完整牌序复现率22.42%，频率基线6.48%；两者差值的配对整局
bootstrap 95%区间为13.56–18.41个百分点。该区间和上表的牌阵汇总比例是不同统计口径。
这不是战斗胜率或真实游戏段位，也不能与使用另一批测试局的v1百分比直接作配对比较。

训练作业总时长339.77秒，最终评测9.13秒，均使用现有单卡T4。账本保守预留共7800秒，
包含旧部署/试运行额度、新三种子作业上限和最终评测上限，不是实际GPU消耗。
主模型约22.4MB推理权重已备份本机且SHA-256一致，完整训练检查点均保留服务器。

首次选择被Windows CRLF与Linux LF差异拦截后，已保存失败证据并新增换行容忍与真实配置变更拒绝测试。
原训练计划和结果未改；`release-plan.json` 只更新配置校验器源码。最终评测远端成功后SSH回传超时，
通过新连接取回并核对完成报告，没有重跑测试。一次性使用账本仍保留。

战斗状态、行动和结算。白名单内容全部可执行且没有未解释规则差异后，才开始S2战斗奖励训练。

## S2基础初始化实现

`yixian/combat_initialization.py`按已固定的客户端`CreateTempData`和`GetStartMaxHp`指令恢复基础状态。
它明确停在`InitData`和`OnBattleStarted`效果之前：境界基础生命加`lastRoundData.extraMaxHp`作为
初始HP和上限，灵气/防御的基础值为0，保留牌序及刻印牌，不重放取得奖励。
缺失字段直接报告不完整；不会从战后数值补齐，境界字段不一致也会单独标记。

在原来64个训练局的525条快照上，1050份双方基础状态全部成功恢复，两处境界字段均一致，
候选基础HP为38–170。这里只验证了输入可恢复及实现与固定初始化证据一致；回放没有直接提供
对应的初始HP供比较，永久状态和仙命尚未执行，不能称为完整开局状态或当前服务器校准通过。
报告为`runs/calibration/20261111T1648-base-initialization-fixed/report.json`。

龙瑶仙命复核分开记录阶段：24为首轮/化神抽牌；25已有战斗组件；85/86取得卡牌15/16；
27除了命元扣除最多20，还包括命元首次≤20时永久升级1张牌及优先规则。
本轮只完成阶段复核，没有把部分组件升级为完整仙命实现。

21项相关软件测试在本机及服务器通过，GPU作业和数据下载均为0。首次实验登记因整数JSON键被
拒绝，发生在读取原始回放前；修正契约并增加回归检查后使用新目录，原计划/源码/失败证据保留。
服务器预检发现缺少境界表，已补齐并核对哈希。已有模型、输入编码和训练结果未改动。

下一轮接永久状态与开局效果，补龙鳞的完整结算及一次升牌奖励，并逐步建立确定性终局差分。
